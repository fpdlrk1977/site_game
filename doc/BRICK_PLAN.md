## 1. 연속 드래그 배치 / 삭제

### 기대 동작
- **지우기**: 좌버튼을 누른 채 끌면 **지나가는 브릭이 계속 지워진다.** 벽 허물기·바닥 걷어내기가 한 번에 된다.
- **놓기**: 지금과 같다 — 클릭 한 번에 **하나**, 누른 채 끌면 **그 브릭 하나가 미끄러진다**(자리 미세조정).
- 드래그 한 획(누름→끌기→뗌)은 **되돌리기 한 번**이다. 20개를 지웠어도 `Ctrl+Z` 한 번에 다 돌아온다.
- 이미 지운 자리를 다시 지나가도 아무 일도 안 일어난다(같은 획에서 중복 처리 없음).

### 안 하는 것
- **놓기 연속 배치는 이 항목에서 하지 않는다**(→ §1-b로 분리).
  > **⚠️ 근거가 바뀌었다(2026-07-31)**: 원래는 "넓게 까는 건 3번(영역 복사)이 맡는다"였다.
  > **3번을 철회했으므로 그 근거는 사라졌다.** 남은 이유는 "드래그가 자리 미세조정과 충돌한다" 하나뿐이고,
  > 그 미세조정 자체가 필요한지도 다시 봐야 한다(§1-b 결정 필요).
- 브러시 크기·직선 모드(Shift) 없음.

### 방식
- `BrickBuilder`에 `eraseStrokeRef`(이번 획에서 지운 id `Set`) 추가.
- `pointerdown`(지우기 도구) → `beginBatch()` → 지우기 → `pointermove` 중 `hoverBrick`이 바뀌면 계속 지운다 → `pointerup`에 `endBatch()`.
- **지우기 판정은 지금 쓰는 `hoverBrick`을 그대로 쓴다** — 새 레이캐스트를 만들지 않는다(이미 매 프레임 갱신된다).
- 되돌리기는 이미 `beginBatch`/`endBatch`가 있으므로 **추가 설계 없음**.

### 닿는 파일
`components/brick/BrickBuilder.tsx` (단독)

### 검증
- 스토어 테스트: 지우기 20회를 한 배치로 묶고 `undo()` 한 번 → 20개가 모두 돌아온다.
- 브라우저: 벽을 드래그로 허물기 · `Ctrl+Z` 한 번에 복구 · 놓기 드래그는 지금과 동일한지.

### 위험
- **🔴 실제로 터졌다(2026-07-31)**: 커서가 브릭을 벗어나면 **그 뒤의 바닥까지 지워졌다**(거리 무관).
  → **획 잠금**으로 해결(`lib/brick/eraseStroke.ts`): 첫 클릭에서 **갈래 · 층 · 도달 거리(12m)** 를 잠근다.
  한 획으로 여러 층은 못 지운다 — 예측 가능한 쪽을 택했다.
- **지우기 드래그가 카메라 회전과 겹치지 않는다**(회전은 우버튼). 안전.
- 지형을 드래그로 파면 `deepenAround`가 획마다 여러 번 돈다 → 한 획에서 같은 기둥은 한 번만 파도록 `Set`으로 막는다.

## 2. 자유 색 선택

### 기대 동작
- 도구 패널의 색 팔레트 옆 **`+` 버튼** → 색 고르개가 열린다.
- 고르개: **색상환(Hue) + 명도/채도 사각형 + HEX 입력**. 고르는 즉시 현재 색이 된다.
- 방금 쓴 색은 **최근 색**으로 남는다(최대 10개, **새로고침해도 유지**).
- 기본 팔레트 10색은 그대로 둔다 — 레고 느낌의 기준색이라 빠르게 집을 수 있어야 한다.

### 안 하는 것
- 색 이름·레고 공식 색 코드 매칭 없음.
- 스포이드(화면에서 색 집기) 없음 — 씬 안 브릭 색을 집는 건 3번(선택) 이후에 자연스럽다.
- 그라데이션·투명도 없음(재질은 `mat`가 따로 담당한다).

### 방식
- **저장은 손댈 것이 없다.** 청크 팔레트가 `[matClass, r, g, b]`로 **임의 RGB를 이미 저장**한다(`serialize.ts`).
  같은 색을 여러 번 써도 팔레트에 한 번만 들어가므로 색을 늘려도 용량이 안 는다.
- 신규 `components/brick/BrickColorPicker.tsx` — **브릭 전용, 자체 완결.**
  > 구 `ColorPicker`는 되살리지 않는다. 씬 `colorAssets`·그라데이션·스포이드·팝업 싱글턴이 얽혀 600줄이 넘었고,
  > 그중 브릭에 필요한 건 "색 하나 고르기"뿐이다.
- 최근 색은 **`localStorage`에 직접**(`lib/brick/colorPrefs.ts`).
  > **⚠️ 계획 수정(2026-07-31, 구현 중 발견)**: 처음엔 `BrickStorage.saveSettings`에 얹으려 했으나
  > **Supabase 어댑터의 `saveSettings`/`loadSettings`가 no-op**이다 — 에디터(db 백엔드)에선 아무것도 저장되지 않는다.
  > (`studStyle`도 사실 프로토타입에서만 유지되고 있었다.)
  > 게다가 최근 색은 **씬 데이터가 아니라 기기/사용자 취향**이라 씬마다 달라지는 것도 이상하다.
  > → 씬과 무관한 `localStorage` 키 하나로 둔다.

### 닿는 파일
`components/brick/BrickColorPicker.tsx`(신규) · `BrickToolPanel.tsx` · `lib/brick/storage.ts`(`BrickSettings.recentColors`) · `store/brickStore.ts`

### 검증
- 브라우저: 임의 색으로 놓기 → 새로고침 → 색 유지 · 최근 색 유지 · 팔레트 색과 섞어 쓰기.

### 위험
- 낮음. 저장 포맷·렌더 경로를 안 건드린다.

## 3. ~~영역 선택 / 복사~~ — ❌ **철회 (2026-07-31)**

> 만들어서 붙여 본 뒤 **사용자가 제동을 걸었다**: *"select가 작업 범위 정할 때 없었던 것 같은데 언제 튀어나왔나.

**"브릭에서 선택이 무엇인가를 정하는 일"** 이라며 3순위로 올렸고, 심지어 **"놓기 연속 배치를 안 만드는 근거"** 로도 썼다.

**철회 사유 셋**

1. **단계가 너무 많다.** 도구 전환 → 드래그 → ↑↓ → Ctrl+C → Ctrl+V → 클릭 → Esc.
   개념 일곱 개를 배워야 바닥 한 장을 깐다. 브릭의 강점은 "클릭하면 붙는다"인데 정반대다.

3. **핵심 루프에 없어도 된다.** 짓고·되돌리고·저장하고·게시하는 한 바퀴는 이것 없이 이미 돈다.

## 1-b. 연속 놓기 (넓게 깔기) — ✅ 구현 완료(2026-07-31) · 브라우저 확인 대기

> 3번을 철회하며 **진짜 필요**만 남겼다. 새 개념을 하나도 안 만든다.

### 기대 동작
- **놓기 도구로 누른 채 끌면 지나가는 칸에 계속 놓인다** — 바닥 한 층, 벽 한 면이 한 번에.
- 지우기와 **똑같은 규칙**으로 잠긴다: 같은 갈래 · 같은 층 · 도달 거리(`eraseStroke.ts` 재사용).
- 한 획 = 되돌리기 한 번.

### ✅ 결정 — (a) 자리 미세조정을 없앤다 (2026-07-31)
미세조정은 **배치가 한 칸씩 어긋나던 시절의 보정책**이었다. 그 문제는 "겨눈 칸의 옆 칸"으로 고쳤고 사용자도 확인했다.
**존재 이유가 사라진 기능이 연속 놓기를 막고 있었다.** `SlidePlane`·`moveBrick`·`slideAnchor` 사용처를 걷어냈다.

### 방식 (구현됨)
- `eraseStroke.ts` → **`strokeLock.ts`** 로 승격(놓기·지우기 공용).
- **★ 판정 대상이 다르다**: 지우기는 **커서 밑 브릭**(갈래·층·거리), 놓기는 **새 브릭이 앉을 자리**(층·거리, **갈래 무시**).
  바닥을 훑으면 커서가 곧 **방금 놓은 브릭의 옆면**을 짚으므로, 짚은 것으로 판정하면 **한 칸 놓자마자 끊긴다**.
- 연쇄 정리: `moveBrick` 제거 → 그것이 만들던 `add/del` 쌍이 사라져 `compact()`도 제거(방어는 `resolveId`가 유지).

### 검증
스토어 테스트: 한 획으로 N개 놓기 → `undo()` 한 번에 전부 사라짐 · 획 잠금이 다른 층엔 안 놓음.
브라우저: 바닥 한 층 드래그로 깔기 · 벽 한 면 · `Ctrl+Z` 한 번.

## 4. 경사 파츠 — ✅ 구현 완료(2026-07-31) · 브라우저 확인 대기

### 기대 동작
- 파츠 갈래에 **`경사`**가 추가된다(브릭·플레이트 옆).
- 처음엔 **3종**: `1×2 경사`(45°) · `2×2 경사` · `1×2 역경사`(뒤집힌 것, 지붕 처마·계단 마감용).
- `R`로 네 방향 회전. 놓는 규칙은 지금과 같다(겨눈 칸의 옆 칸).
- 지붕·언덕·계단 옆면을 각지지 않게 마감할 수 있다.

### 안 하는 것
- 곡면·원기둥·창문·문 같은 특수 파츠.
- 경사 위에 브릭을 얹었을 때 **틈을 자동으로 메우지 않는다**(레고도 안 그런다).

### 방식
- `PARTS`에 `shape: 'box' | 'slope' | 'slopeInv'` 추가(미지정=box → **기존 파츠 전부 무변경**).
- `PART_ORDER` **뒤에만 추가**(append-only 규칙 — 앞에 끼우면 저장된 청크가 다른 파츠로 읽힌다).
- 지오메트리: `brickGeometry`에 쐐기(wedge) 분기. 돌기는 **윗면 평평한 부분에만**.
- **★ 가시성 규칙이 핵심**: 지금은 "이웃 칸이 차 있으면 그 면을 감춘다"인데, 경사는 칸을 차지하면서도
  **대각선이 뚫려 있어** 감춘 면이 그대로 보인다(구멍처럼 보임).
  → 경사는 **칸은 점유하되(그 자리에 못 놓음) 이웃 면을 감추지 않는다**(non-occluding).
  마인크래프트가 계단·반블록에 쓰는 방식과 같다. 면 몇 개가 더 그려지는 비용은 작다.

### 결정 필요 ②
**경사 3종으로 시작하는 것이 맞나?** 더 필요하면(예: `2×4 완만한 경사`, `코너 경사`) 지금 말해 주시면 함께 넣는다.
코너 경사는 지오메트리가 까다로워 **1차에서는 빼는 것을 추천**한다.

### 닿는 파일
`lib/brick/parts.ts` · `lib/brick/brickGeometry.ts` · `lib/brick/world.ts`(가시성 판정) · `BrickToolPanel.tsx`

### 검증
- 지오메트리 테스트: 쐐기의 높이/폭이 칸 규격과 맞는지 · 삼각형 수.
- 저장 테스트: `PART_ORDER` 추가 후 **기존 청크가 그대로 읽히는지**(가장 중요 — 어긋나면 남의 저장물이 다른 파츠로 바뀐다).
- 브라우저: 경사로 지붕 만들기 · 경사 옆·아래에서 구멍이 안 보이는지.

### 위험
- **`PART_ORDER`를 앞에 끼우면 저장된 모든 씬이 깨진다.** 테스트로 잠근다.
- 경사를 non-occluding으로 두면 경사가 많은 씬에서 면이 늘어난다 → 지붕 한 면 정도는 영향 미미.

## 5. 부드러운 조명 (정점 단위 밝기) — ✅ 구현 완료(2026-07-31) · 브라우저 확인 대기

### 기대 동작
- 지금은 **면 하나가 통짜로 같은 밝기**라, 벽 모서리·구덩이 안이 계단처럼 각져 보인다.
- 바꾸면 밝기가 **면 안에서 부드럽게 번진다** — 구석은 어둡고 열린 쪽은 밝게(앰비언트 오클루전 느낌).
- 조명 모델 자체는 그대로다(하늘빛 전파 × 면 방향 배율). **입체감만 부드러워진다.**

### 안 하는 것
- 실시간 그림자·방향광 — 되돌아가지 않는다(그건 브릭 룩을 망가뜨린 원인이었다).
- 색 있는 조명·발광 브릭 — 별개 항목.

### 방식 — ★ 구현에서 **8꼭짓점**으로 바뀜 (계획의 24값은 폐기)
- 계획은 `6면 × 4꼭짓점 = 24값`(vec4 6개)이었으나, `instanceMatrix`가 이미 4칸을 먹어
  **정점 속성 한도(16)에 위험하게 붙는다.** → **브릭의 꼭짓점 8개**만 넘긴다(`aCornerA/B` = vec4 둘,
  **속성 개수가 전과 같다**). 한 꼭짓점을 세 면이 공유하지만 각 면은 **자기 쪽 네 꼭짓점**만 써서 실사용에선 티가 안 난다.
- 지오메트리는 정점마다 **삼선형 가중치**(`aSelA/aSelB`)를 들고, 셰이더가 `dot`으로 섞는다.
  → 상자 모서리에선 자동으로 one-hot이 되고 **돌기·경사처럼 면 한가운데 있는 정점**도 자연스럽게 섞인다.
- **면 방향 배율은 셰이더가 월드 법선으로** 곱한다(꼭짓점을 세 면이 공유하므로 CPU에서 못 곱한다).

### 5-b. 구석 그늘(AO) — ✅ 추가 구현(2026-07-31)
하늘빛만으로는 **열린 하늘 칸이 전부 1.0**이라 브릭 옆·모서리가 전혀 어두워지지 않는다(실측: 평지에 브릭을 놓아도 주변 576개 중 **변한 것 0개**).
→ 꼭짓점마다 **바깥 일곱 칸 중 막힌 칸 수**로 깎는다.
- **기준은 `FLAT`(=3)** — 평평한 면의 꼭짓점은 항상 이웃 셋이 막혀 있다. 거기서 **더** 막힌 만큼만 깎으므로
  **평평한 면·볼록 모서리는 1.0 그대로**, 오목한 구석만 어두워진다. **밝아지는 곳은 없다**(전역 밝기 불변).
- 이 기준을 안 잡고 `blocked/8`로 깎으면 **바닥 전체가 통째로 어두워진다** — AO가 아니라 그냥 조광이 된다.

### 결정 필요 ③ — ✅ 해소
"돌기·경사는 면 평균으로 두자"던 절충은 **불필요해졌다.** 삼선형 가중치가 그 정점들까지 한 번에 처리한다.

### 5-c. 그늘이 번지는 폭 — **줄일 필요 없었다** (2026-07-31)

밝기 값이 **꼭짓점 여덟 개에만** 있고 그 사이는 래스터라이저가 선형 보간한다.
→ 그라데이션이 **면 전체**에 깔리고, 지형 타일이 2×2칸(**1m**)이라 그늘도 1m를 먹는다.

**★ 정정**: 이걸 한계로 적었는데, **마인크래프트도 블록 1개(1m) 폭이다.** 폭은 이미 같았고
문제는 **세기 곡선**이었다(선형이라 첫 접촉이 약했다). → **5-e에서 해결.**
아래 표는 그래도 남겨 둔다 — 0.5m 이하로 더 또렷하게 만들고 싶어지면 그때 필요한 정보다.

선택지 셋. **지금은 1번**.

| | 내용 | 비용 | 결과 |
|---|---|---|---|
| **1. 연하게 두기(현재)** | 은은한 음영으로만 쓴다 | 0 | 접지 그늘이 부드럽지만 넓다 |
| **2. AO 빼기** | `cornerAO`만 지우면 된다 | 0 | 1m 얼룩이 거슬리면 이게 정직하다 |
| **3. 지형만 리전 메시로 합치기** | 지형은 회전·색 변화가 없어 합치기 좋다. 바닥에 **칸 단위(0.5m) 이하**의 또렷한 그늘 | ⑥급 작업 — 저장·스트리밍·피킹이 지형 경로만 갈라진다 | 마인크래프트와 같은 구조 |

> 3번은 **계획에 없던 항목**이다. 넣으려면 여기 먼저 적고 확인을 받을 것.
> 정점마다 다른 밝기를 주려면 리전 지오메트리를 합쳐야 하고, 그건 **인스턴싱 포기**를 뜻한다.

### 5-d. 면 배율(`FACE_TONE`) 확대 — ✅ 적용(2026-07-31)

번짐 없이 입체감을 키우는 길은 AO가 아니라 **면 배율**이다. 배율은 면마다 상수라 **모서리에서 딱 끊긴다**(보간 없음).
앞뒤 `0.8→0.72` · 좌우 `0.6→0.5` · 밑면 `0.5→0.35`. **윗면은 1.0 유지** — 바닥 밝기가 변하면 씬 전체 톤이 흔들린다.
비용 0(셰이더 상수). 환경광은 안 건드렸다(윗면이 그대로라 기준 밝기가 유지된다).

### 5-e. AO 응답 곡선 — 선형 → `√` ✅ 적용(2026-07-31)

**사용자 확인으로 목표가 분명해졌다: "마인크래프트에서 블록을 바닥에 놓으면 접촉면에 지는 강한 그늘".**
그건 방향광 그림자가 아니라 **AO**다 — 마인크래프트엔 방향광도 그림자 맵도 없다. 즉 **그림자 맵은 필요 없다**(아래 5-f).

선형 응답으로는 양쪽이 다 안 됐다:

| 세기(선형) | 벽 하나(밑동) | 깊은 구석 | 판정 |
|---|---|---|---|
| 0.7 | 0.82 | 0.30 | **밑동이 안 보인다**(사용자) |
| 2.0 | 0.50 | 0.20 | **깊은 구석이 새까매 얼룩**(사용자) |
| **√ 0.6 (채택)** | **0.70** | **0.40** | 밑동은 진하고 구석은 안 뭉갠다 |

**첫 접촉에서 크게 떨어지고 그 뒤는 완만한 모양**이 핵심이다. 테스트는 값이 아니라 **낙차가 줄어드는지**(오목)를 잠근다 —
선형으로 되돌리면 낙차가 `0.15 / 0.15 / 0.15`로 균일해져 실패한다(사보타주로 확인).

### 5-g. ★ 그늘의 **공간 프로파일** — 셰이더 곡선 ✅ 적용·확인 완료(2026-07-31)

세기를 0.7↔2.0으로 오가며 두 번 헛돌았던 진짜 이유. **문제는 세기가 아니라 떨어지는 모양이었다.**
정점 사이는 래스터라이저가 **직선**으로 섞으므로, 세기를 올리면 띠가 좁아지는 게 아니라 **넓은 얼룩이 진해질 뿐**이다.

→ 프래그먼트에서 부족분에 지수: **`1 - pow(1 - sky, SHADE_CURVE)`**(1.6).

| 벽에서의 거리 | 직선 | 곡선 |
|---|---|---|
| 접촉면 | 0.70 | **0.56** |
| 반 칸(0.5m) | 0.85 | 0.85 |
| 한 칸(1m) | 1.00 | 1.00 |

- **면 배율은 별도 varying**(`vBaked = vec2(sky, tone)`) — 배율은 면마다 상수라 곡선을 씌우면 안 된다.
- **`AO_STRENGTH`(1.2, `world.ts`)와 `SHADE_CURVE`(1.6, `BrickInstances.tsx`)는 한 쌍.** 한쪽만 바꾸면 무너진다.
- 조이는 법: `SHADE_CURVE`↑ = 더 좁고 진하게 · `AO_STRENGTH`↑ = 전체적으로 진하게.

### 5-h. 환경광은 `π` ✅ (2026-07-31)

three는 환경광을 **`intensity / π`** 로 쓴다. `Math.PI`여야 **알베도 1:1**(고른 색 그대로·흰색은 255)이고, 그 위에서 면 배율·AO가 깎기만 하므로 잘리지 않는다.
낮추면 바닥이 어두워져 **같은 배율이라도 그늘이 안 보인다**(1.0일 때 갈색 바닥 61/그늘 46 → `π`에서 107/88). 자세한 경위는 `BRICK_PROGRESS.md` D-2b·D-2c.

### 5-f. ❌ 방향광 + 그림자 맵 — 안 한다 (2026-07-31 재확인)

"자연광이면 물체 그림자가 져야 하지 않나"에서 출발했지만, 목표가 마인크래프트 룩이면 **오히려 룩을 깬다.**

- 마인크래프트엔 태양 방향이 없다. 밑동 그늘의 정체는 AO다.
- 되살리면 **"블록에 그림자가 진다"·"카메라 돌리면 번쩍인다"** 가 재발한다 — 그때 **두 번 버그로 신고된** 현상이다(`BRICK_PROGRESS.md` D-1).
- 실측 **+10.3ms**. 프레임 예산 16.7ms의 절반이 넘고, 그림자 맵은 카메라 컬링이 안 먹어 삼각형이 4배(157K→623K).

반면 5-d·5-e는 **추가 비용 0**이다(상수·수식만 바뀜).

### 닿는 파일
`lib/brick/world.ts`(꼭짓점 빛 계산) · `components/brick/BrickInstances.tsx`(attribute·셰이더)

### 검증
- 월드 테스트 102/102: 꼭짓점 값이 **배율 없는 순수 하늘빛**인지 · 걸친 브릭이 먼 쪽 꼭짓점을 안 건드리는지 ·
  **평평한 바닥은 1.0 그대로 / 벽에 닿은 구석만 어두워지는지** · **빛을 다시 구우면 리전 리비전이 오르는지**.
- 성능 실측: **15ms**(사용자 측정, 되돌림 기준 50ms 이내).
- 브라우저: 구덩이 안·벽 모서리가 부드러운지, 계단 무늬가 사라졌는지.

### 위험
- 굽는 비용이 늘었다(면 6 → 꼭짓점 8 × 8칸). 실측 15ms로 여유 있음.
- 셰이더 보간이 틀리면 **면이 뒤집힌 것처럼 얼룩진다** — 눈으로 바로 보이므로 발견은 쉽다.
- **★ 다시 구운 값을 렌더러에 알리는 것을 잊기 쉽다** — 실제로 잊어서 "브릭을 놓으면 그림자가 사라진다"가 났다.
  `recomputeLight()`는 굽기가 끝나면 **리전 전량 `bumpRegion`** 한다. 자세한 건 `BRICK_PROGRESS.md` G-6.

## 6. 청크 콜라이더 (걷기)

### 기대 동작
- 뷰어·에디터에서 **`▶ 걷기`**로 들어가면 1인칭/3인칭 캐릭터가 브릭 위를 **걸어 다닌다**.
- 브릭·지형에 막히고, 브릭 위로 올라선다. **한 칸(0.2m) 높이는 자동으로 올라간다**(계단 오르기).
- 낙사 없음 — 바닥 밑으로 떨어지면 지면으로 되돌린다.
- 나가면 원래 카메라로 복귀.

### 안 하는 것
- 점프·수영·사다리·탈것.
- 물리 시뮬레이션(밀리는 상자, 떨어지는 브릭). 브릭은 **고정**이다.
- 다른 사람과 같이 걷기(→ 7번).

### 방식
- **물리 엔진을 다시 들이지 않는다.** `@react-three/rapier`는 2d에서 지웠고, 되살릴 이유가 없다:
  브릭 월드는 **정렬된 격자**라 캡슐-격자 충돌을 직접 푸는 편이 더 단순하고, 결정적이며, **테스트가 된다.**
- 신규 `lib/brick/walk.ts` — 순수 함수:
  `moveCharacter(occupancyLookup, pos, radius, height, delta) → newPos`
  축별 스윕(swept AABB) + 계단 오르기 + 중력. 월드의 `at(x,y,z)`만 있으면 되므로 렌더와 무관하다.
- 컨트롤러는 `BrickWalker.tsx`(카메라·입력). 구 `PlayModeController`(625줄)는 **참고만** 하고 가져오지 않는다 — 오브젝트·이벤트·상호작용이 얽혀 있다.

### 결정 필요 ④
**어디에 붙일 것인가**: 에디터에도(짓다가 걸어보기) / 뷰어에만(방문자용) / 둘 다.
→ **둘 다**를 추천한다. 코드는 같고, 에디터에선 "지은 걸 바로 걸어본다"가 크다.

### 닿는 파일
신규 `lib/brick/walk.ts` · 신규 `components/brick/BrickWalker.tsx` · `BrickScene.tsx`(모드 전환)

### 검증
- **순수 함수 테스트가 핵심**: 벽에 막힘 · 바닥에 섬 · 한 칸 자동 오르기 · 두 칸은 못 오름 · 모서리 끼임 없음 · 빈 공간 낙하.
- 브라우저: 지은 집 안을 걸어 다니기.

### 위험
- 캐릭터가 **브릭 사이에 끼는** 고전적 버그 → 축별 스윕과 여유값(skin)으로 막고 테스트로 잠근다.
- 스트리밍 경계 밖으로 걸어 나가면 그 앞이 비어 있다 → 걷기 중엔 **스트리밍 기준점을 캐릭터로** 바꾼다.

## 7. 청크 동기화 (협업)

### 기대 동작
- 같은 씬을 두 사람이 열면 **상대가 놓는 브릭이 실시간으로 보인다.**
- 상단에 접속자 아바타. 상대가 보고 있는 위치를 흐리게 표시(선택).
- 같은 자리에 동시에 놓으면 **먼저 도착한 쪽이 이긴다**(둘 다 놓이지 않고 하나만).

### 안 하는 것
- 되돌리기 공유(내 `Ctrl+Z`가 남의 브릭을 지우지 않는다 — 각자 자기 것만).
- 음성·채팅·권한(편집자/보기 전용).

### 방식
- **CRDT를 다시 들이지 않는다.** 지웠던 Yjs 문서는 `objects` 배열용이었고, 브릭엔 맞지 않는다.
- Supabase Realtime **broadcast로 명령을 주고받는다** — `{op:'place'|'remove', 브릭 데이터}`.
  되돌리기가 이미 같은 모양의 명령을 쓰고 있어 **그대로 얹힌다.**
- 충돌은 **월드가 판정**한다: `place`는 이미 막힌 자리면 `null`을 낸다 → 늦게 온 쪽이 자동으로 진다. 별도 규칙 불필요.
- 늦게 들어온 사람은 **저장소에서 읽는다**(이미 청크 단위 로딩이 있다) → 초기 동기화 코드가 따로 없다.
- 저장은 **각자 자기 편집분만** 쓴다(청크 단위라 겹쳐도 마지막 쓰기가 이긴다). 정확히 하려면 서버 쪽 병합이 필요한데, 그건 이 범위 밖.

### 결정 필요 ⑤
**Pro 플랜 기능으로 묶을 것인가?** (요금제 표에 이미 "실시간 협업"이 Pro로 적혀 있다)
→ 기능이 동작한 뒤에 게이팅을 붙이는 것을 추천한다(개발 중엔 열어 둔다).

### 닿는 파일
신규 `lib/brick/sync.ts` · `store/brickStore.ts` · `BrickScene.tsx`

### 검증
- 두 브라우저 창으로: 한쪽이 놓으면 다른 쪽에 보임 · 같은 자리 동시 배치 · 새로고침 후 일치.

### 위험
- **저장 경합**: 두 사람이 같은 청크를 고치면 마지막 저장이 이긴다(브릭 하나가 사라질 수 있다). 1차 범위에서는 감수하고 명시한다.
