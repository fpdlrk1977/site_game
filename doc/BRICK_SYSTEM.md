## 0. 왜 이걸 하는가

에디터에서 테이블 하나를 만들어보니 이랬다:

> 박스를 만들고 → 크기를 조정하고 → 다리를 놓으려는데 상판과 맞추려면
> 기즈모를 이리저리 움직이고 카메라를 돌려야 했다.

원인은 복셀이 없어서가 아니라 **에디터에 "상대 배치"라는 개념이 없기 때문**이었다. 확인한 사실:

| 확인 | 현재 |
|---|---|
| 오브젝트 배치 (`EditorCanvas.tsx:922`) | `groundPointFromEvent` — **항상 바닥(y=0) 평면에만** 떨어짐 |
| 그리드 스냅 (`sceneStore.ts:632`) | `snapEnabled: false` — 기본 꺼짐 |
| 오브젝트 스냅 (`sceneStore.ts:635`) | `objectSnap: false` — 기본 꺼짐, 가이드선 없음, 그룹 제외 |
| 정렬 (`alignSelected`) | min/center/max 맞추기뿐 — **"A 위에 B 올리기"가 없음** |

모든 배치가 절대 좌표 + 눈대중이었다. 그래서 **격자 기반 조립을 주력 경로로 세운다.**

### 훔쳐올 것 — 마인크래프트의 핵심 상호작용

> **보이는 면을 클릭하면, 새 블록이 그 면에 정확히 맞닿아 생긴다.**

두 가지 성질이 여기서 나온다. ①어긋날 수가 없다(인접이 계산됨) ②카메라를 돌릴 필요가 없다(안 보이는 면은 클릭 대상이 아님).

참고: 이 메커니즘은 이미 `VoxelToolModal.tsx:62-67`에 있다(`e.face.normal`로 인접 칸 계산). 모달 밖으로 꺼내 임의 크기 브릭으로 일반화하는 것이 이 작업이다.

## 1. 확정 사항

**시스템 = 마인크래프트 / 형태 = 레고 브릭.** 모양만 브릭이고 동작 구조는 마크를 따른다.

| # | 항목 | 확정값 |
|---|---|---|
| 1 | 세로 높이 | **512칸** (`y = -64 … +447`) = 지하 12.8m ~ 지상 89.4m |
| 2a | 브릭 크기 | **캐릭터가 위를 걸어다니는 크기** (스터드 간격 0.5m) |
| 2b | 격자 눈금 | **레고 비율** — 셀 0.5 × **0.2** × 0.5 m, 브릭 = Y 3칸 |
| 3 | v1 파츠 | 1×1 · 1×2 · 2×2 · 2×4 |
| 4 | v1 재질군 | 불투명 / 반투명 / 발광 + 색 자유 (질감 없음) |
| — | 가로 | **무제한** (무한 맵) |

### 1·2는 되돌릴 수 없다

`y` 값은 "몇 번째 칸"이라는 정수로 저장된다. 눈금 높이를 바꾸면 **저장된 모든 브릭이 엉뚱한 높이로 내려앉는다.** 3·4(파츠·재질)는 저장 포맷을 안 건드리므로 언제든 추가 가능하다.

### 2b를 레고 비율로 잡은 이유

셀 높이 = **플레이트(얇은 판) 높이**로 두면 두꺼운 브릭(3칸)과 얇은 판(1칸)을 **둘 다** 놓을 수 있다. 정육면체 격자면 브릭보다 얇은 것은 영원히 불가능하다 — 지붕 경사, 바닥 마감, 얇은 창틀이 안 나온다.

**v1엔 플레이트를 만들지 않아도 된다.** 지금은 눈금만 촘촘히 잡아 자리를 비워두는 것이다.

사용자는 촘촘한 눈금을 의식하지 않는다 — 브릭 배치 시 자동으로 3칸 단위로 스냅되고, 눈금이 드러나는 건 나중에 플레이트를 쓸 때뿐이다.

## 2. 채택 / 미채택 (결정 로그)

마인크래프트 설계의 절반은 *무한 절차 생성 월드* 때문에 존재한다. 우리는 그게 아니므로 갈라서 받는다.

### ✅ 채택

| 항목 | 이유 |
|---|---|
| 격자 배치 | 어긋날 수 없음 = 원래 문제의 해답 |
| 면 인접 배치 | 카메라 회전 불필요 |
| 블록 타입 카탈로그 | 무한 파라미터 → 유한 목록 (사용자에게 더 쉬움) |
| 청크 + 스트리밍 | **무한 맵의 필수 조건** |
| 광원 전파 + 정점 AO | 이게 없으면 룩이 납작하다 |
| 세로 높이 제한 | 청크 컬럼 성립 조건 |
| 면 제거 (묻힌 것 스킵) | 최대 효과 최소 비용 |
| 인스턴싱 | 브릭에 맞는 렌더 전략 |
| frustum culling | 청크 나누면 공짜 |
| 십자 조준 (플레이) | `ViewerCanvas.tsx:336-343`에 이미 있음 |

### ❌ 미채택

#### 그리디 메싱 — 절대 금지

같은 텍스처의 인접 평면을 큰 사각형으로 병합하는 기법. **바닐라 마인크래프트도 안 한다**(면 제거만 함). 클론·모드가 쓰는 별도 기법이므로 "마크 시스템 채택"에 포함되지 않는다.

1. **브릭엔 합칠 평면이 없다** — 스터드(돌기) 때문에 인접 브릭 윗면이 평면이 아니다. 이득 ≈ 0
2. **파츠별 색이 불가능해진다** — 병합 사각형이 여러 브릭에 걸치는데 색이 다르면 못 합친다. 색이 많을수록 이득 소멸. 그런데 파츠별 색은 필수 요구사항
3. **클릭한 브릭을 알 수 없다** — `instanceId`가 사라져 복셀 DDA를 직접 구현해야 함
4. **하나 놓을 때마다 청크 전체 리메시** — 인스턴싱은 행렬 1개만 갱신

→ 대신 **면 제거 + 스터드 컬링**.

#### 절차적 지형 생성

시드+노이즈로 지형을 계산. 마크의 무한은 이것이다(저장이 아니라 계산).

우리는 **저작 도구**라 사용자 의도와 무관한 지형이 튀어나오면 안 된다. 생성 규칙(바이옴·동굴·광맥) 자체가 큰 시스템이다.

→ 대신 **희소 저장 + 가상 바닥**(§3.4).

#### 마크식 네트워크 동기화

권위 서버 + 클라 예측 + 지연 보상. 우리 문제는 **동시 편집**이지 실시간 게임플레이가 아니다.

| | 마크 넷코드 | 우리 |
|---|---|---|
| 빈도 | 초당 20틱 연속 | 드문드문한 이산 편집 |
| 권위 | 서버 | 불필요 (CRDT 수렴) |
| 예측/보정 | 필수 | 불필요 |
| 이미 있는 것 | — | **Yjs + Supabase Realtime** |

→ 나중에 기존 Yjs에 **청크 단위 CRDT** 확장 (P6).

### ⏸ 보류

| 항목 | 왜 나중에 | 대신 지금 |
|---|---|---|
| **LOD** | 다중 해상도 청크 데이터를 따로 유지 → 저장·메싱·갱신 전부 2배. 효과는 시야 아주 멀 때만 | **시야 거리 제한 + 안개** (마크도 기본 12청크). fog·far plane 이미 있음 |
| **오클루전 컬링** | 청크만 나눠도 frustum이 대부분 커버. 실내·동굴 많아야 값을 함 | 청크 + frustum, 프로파일 후 재검토 |
| **유체 시뮬** | 마크에서도 가장 복잡·버그 많은 축(흐름 상태·갱신 큐·청크 경계 전파) | **정적 물 블록** — 시각 가치 80%를 2% 비용으로 |
| **질감 텍스처** | 아틀라스 + 인스턴스별 UV 오프셋 | 색만. 나중에 아틀라스 한 장 얹으면 됨 |

## 3. 좌표계 · 데이터 모델

### 3.1 격자

```
셀 크기    X = 0.5 m   (스터드 간격)
          Y = 0.2 m   (플레이트 높이)   ← 격자 한 칸의 높이
          Z = 0.5 m

비율      0.5 : 0.2 = 2.5 : 1   (실제 레고 8mm : 3.2mm와 동일)
브릭 높이  0.6 m = Y 3칸
```

옆에서 본 모습:

```
  칸6 ┃ ▓▓▓▓▓▓▓ ┃ ┐
  칸5 ┃ ▓▓▓▓▓▓▓ ┃ ├─ 브릭 1개 (Y 3칸)
  칸4 ┃ ▓▓▓▓▓▓▓ ┃ ┘
  칸3 ┃ ░░░░░░░ ┃ ←─ 플레이트 1개 (Y 1칸)  ※v1 미포함, 자리만 확보
  칸2 ┃ ▓▓▓▓▓▓▓ ┃ ┐
  칸1 ┃ ▓▓▓▓▓▓▓ ┃ ├─ 브릭 1개 (Y 3칸)
  칸0 ┃ ▓▓▓▓▓▓▓ ┃ ┘
 바닥 ┗━━━━━━━━━┛
```

**축척 감각**: 캐릭터 1.8m ≈ 브릭 3개 / 방 높이 2.4m ≈ 브릭 4개 / 2×4 브릭 = 1.0 × 0.6 × 0.5 m

**세로 범위**: `y ∈ [-64, +447]` (512칸). 지하 12.8m ~ 지상 89.4m ≈ 30층 건물.
**가로 범위**: 사실상 무제한. 좌표는 `i32`, 실사용은 ±16km 수준.

### 3.2 브릭 레코드 — **셀 배열이 아니다**

마인크래프트는 "1셀 = 1블록"이라 셀 배열이 자연스럽다. **브릭은 여러 셀에 걸치므로 셀 배열은 낭비다**(2×4 브릭 하나가 2×3×4 = 24셀).

→ **저장은 브릭 레코드 리스트, 런타임 조회는 파생 점유 격자.**

```
BrickRecord (10 bytes)
  partId   u16    파츠 종류 (전역 카탈로그 인덱스)
  x, y, z  i16×3  청크 내 상대 좌표 (앵커 셀 = 최소 모서리)
  rot      u8     Y축 4방향 (0/90/180/270)
  matIdx   u8     청크 재질 팔레트 인덱스
```

```
Chunk
  bricks      BrickRecord[]
  matPalette  { class: 'opaque'|'transparent'|'emissive', color: '#rrggbb' }[]
```

**팔레트**를 쓰는 이유: 색을 아무리 많이 써도 레코드는 1바이트만 늘어난다. 마크의 청크 팔레트와 같은 발상.

**점유 격자(occupancy)** 는 저장하지 않는다. 청크 로드 시 레코드에서 파생해 메모리에만 둔다 — "이 칸이 비었나"를 O(1)로 답하기 위한 인덱스.

### 3.3 청크 / 리전 — 두 개는 다른 개념

혼동하면 draw call이 폭발한다. **분리해서 설계한다.**

| | 용도 | 크기 |
|---|---|---|
| **청크** | 데이터·저장·스트리밍 단위 | **16 × 32 × 16 셀** = 8 × 6.4 × 8 m |
| **리전** | 렌더 배칭 단위 (여러 청크를 묶음) | **4 × 4 × 4 청크** = 32 × 25.6 × 32 m |

세로 512칸 ÷ 청크 32칸 = **16 청크층**.

청크마다 파츠 종류마다 `InstancedMesh`를 만들면 200청크 × 12 = 2,400 draw call로 터진다. 리전 단위로 인스턴스 버퍼를 묶으면 보이는 리전 10~20개 × 리전당 (파츠 × 재질군) 12개 ≈ **120~240 draw call**로 수용 가능해진다.

> **v1(P0)에는 청크·리전이 없다.** 메모리에 브릭 리스트 하나, `(파츠 × 재질군)`당 `InstancedMesh` 하나 = **12 draw call**. 청크는 P1~P2에서 도입한다.

### 3.4 가상 바닥 — 무한하고 팔 수 있는 바닥을 공짜로

```
기본 상태     무한 평면 바닥 (현 GroundPlane 그대로 — 저장/렌더 비용 0)
    ↓ 그 자리를 파는 순간
그 청크만 실제 브릭 데이터로 승격(materialize)
    ↓
건드리지 않은 청크는 영원히 저장 비용 0
```

사용자는 손으로 무한을 채울 수 없다. 실제 데이터는 항상 유한하다(청크 수백 개 수준). 그래서 절차 생성 없이도 "무한하고 파낼 수 있는 바닥"이 성립한다. `GroundPlane`에 이미 있는 "Infinite ground" 옵션이 출발점이다.

### 3.5 저장 (P1에서)

기존 테이블은 **손대지 않는다.** 새 테이블만 추가한다(§7).

```sql
-- 0009_bricks.sql  (순수 추가 — 기존 테이블 무수정)
create table if not exists brick_chunks (
  scene_id   uuid not null references scenes(id) on delete cascade,
  cx int not null, cy int not null, cz int not null,
  data       bytea not null,          -- 레코드 + 팔레트, 압축
  updated_at timestamptz default now(),
  primary key (scene_id, cx, cy, cz)
);
```

**희소 저장** — 비어 있지 않은 청크만 행으로 존재하므로 무한 맵의 빈 공간은 비용 0. 로드는 카메라 주변 좌표 범위 쿼리, 저장은 dirty 청크만.

`scenes.scene_data`(jsonb)는 그대로 두고 브릭 월드만 분리한다. 라이트·이벤트·게임로직 등 기존 씬 데이터는 전부 살아 있다.

## 4. 렌더 파이프라인

### 4.1 인스턴싱

```
InstancedMesh 하나 = (파츠 × 스터드변형 × 재질군)
   → 색은 이 안에서 인스턴스마다 자유 (setColorAt — draw call 안 늘어남)
```

`InstancedMesh.setColorAt(i, color)`는 three.js 기본 기능이다. 같은 2×4 브릭 1만 개가 전부 다른 색이어도 **draw call 1개**다.

현 코드 `InstancedPrimitives.tsx:41`은 `setMatrixAt`(위치)만 쓰고 색은 공유 재질에 있다. **`setColorAt` 추가가 필요하다.**

재질군이 나뉘는 이유는 셰이더·렌더 패스가 달라서다:

| 재질군 | 처리 |
|---|---|
| 불투명 | 기본 패스 |
| 반투명 | 별도 패스, `depthWrite=false`, 정렬 필요 |
| 발광 | emissive + **조명 전파의 광원** (P3) |

### 4.2 ⚠️ 폴리곤 예산 — 최대 리스크

브릭은 큐브보다 훨씬 무겁다:

| | 삼각형 | 큐브 대비 |
|---|---|---|
| 마크 큐브 | 12 | 1× |
| 브릭 1×1 (스터드 1개, 8각) | ~36 | **3×** |
| 브릭 2×4 (스터드 8개) | ~204 | **17×** |

브릭 10만 개 × 200 = **2,000만 삼각형** → 그대로는 불가능. 설계에 처음부터 반영한다:

1. **묻힌 브릭 스킵** — 6면이 전부 막힌 브릭은 인스턴스를 만들지 않음
   - 100×100×20 꽉 찬 덩어리: 200,000개 → **껍질만 27,128개 (86% 감소)**
2. **스터드 컬링** — 위가 완전히 덮인 브릭은 *스터드 없는* 메시 변형 사용
   - 파츠마다 메시 2종(스터드 有/無). 부분 가림은 단순화해서 有 유지 (2^8 변형은 비현실적)
3. **원거리 스터드 → 노멀맵** — 먼 리전은 박스(12 tris) + 노멀맵
4. 스터드는 6~8각 저폴리

> 1·2는 **인스턴싱이라서 가능한 최적화**다. 그리디 메싱이면 스터드 하나 가려질 때마다 청크를 다시 구워야 한다.

### 4.3 피킹 (클릭)

```
three.js InstancedMesh raycast → instanceId → 브릭 레코드
                              → 면 법선 → 인접 셀 → 새 브릭 위치
```

**그리디 메싱을 안 쓰는 가장 큰 실익.** 복셀 DDA를 직접 구현할 필요가 없다.

에디터는 마우스 포인터, 플레이 모드는 십자 조준(`centerPointer` — 이미 구현됨).

### 4.4 배치 규칙 (v1)

- 새 브릭의 점유 셀이 **전부 비어 있어야** 배치 가능
- 브릭 배치 시 **Y 3칸 단위로 자동 스냅** (사용자가 촘촘한 눈금을 의식하지 않게)
- 회전은 Y축 4방향
- 스터드 정렬 검사는 v1에서 생략 (격자에 맞으면 OK)

## 5. 블록 타입 — 파츠 × 재질군 × 색

마인크래프트는 형태와 재질이 붙어 있어 카탈로그가 곱해진다(돌 블록 / 돌 계단 / 돌 반블록 …). **브릭은 직교 분해가 가능하다.**

```
BrickType = 파츠(형태) × 재질군 × 색
```

파츠 10종 + 재질 15종 = **25개 정의로 150가지 조합**. 마크였다면 150개를 손으로 정의해야 한다.

| 마인크래프트 | 우리 표현 |
|---|---|
| 돌 / 흙 / 나무 / 모래 | 불투명 + 색 |
| 유리 / 물 | 반투명 + 색 |
| 글로우스톤 / 용암 | 발광 + 색 |

파츠 정의:

```
BrickPart {
  id            'brick_2x4'
  footprint     { x: 2, y: 3, z: 4 }     // 차지하는 셀 수
  mesh          스터드 有 / 無 2종
  collision     AABB (또는 복합)
}
```

타입 정의:

```
BrickType {
  part          'brick_2x4'
  materialClass 'opaque' | 'transparent' | 'emissive'
  color         '#rrggbb'
  opaque        빛을 막는가        (조명 전파 입력)
  lightLevel    광원이면 1~15      (조명 전파 입력)
  collision     통과 가능한가       (물리 입력)
}
```

**UX**: 자주 쓰는 조합을 완제품 팔레트로 띄우되(마크 핫바처럼), 그 팔레트는 파츠 × 재질 조합에서 **자동 생성**한다. 고급 모드에서 자유 조합.

## 6. 기존 시스템과의 경계

**"다 뒤엎기"가 아니라 "조립 방식을 하나로 세우기"다.** 게시·게임로직·물리는 오히려 격자 위에서 더 잘 산다.

| 그대로 남는 것 (직교적) | 흡수 / 은퇴 후보 (검증 후 판단) |
|---|---|
| 게시 · 뷰어 · 임베드 · 커스텀 도메인 | 복셀 모달 → 브릭 시스템으로 흡수 |
| 게임 로직 (변수 · 이벤트 · HUD · 씬 규칙) | Boolean · Merge · Loft |
| 물리 · 플레이 모드 · 캐릭터 | 펜툴 (격자 조립이 대체) |
| 액추에이터 · 모터 | Array / Cloner (일부) |
| 라이트 · 카메라 · 환경 | 조작 핸들 · 앵커 · 스냅 (격자가 곧 스냅) |
| GLB 임포트 (외부 에셋) | |
| 협업 · 애널리틱스 · 커뮤니티 | |

**은퇴는 P0 검증 이후에 결정한다.** 새 방식이 검증되기 전에 기존 걸 걷어내면 돌아갈 데가 없다.

## 7. 마이그레이션 안전 규칙

브랜치를 따도 **Supabase 프로젝트는 하나**다(`.env.local` 공유). 마이그레이션은 브랜치가 아니라 **DB에 적용된다.**

| 하는 일 | main에 미치는 영향 |
|---|---|
| `CREATE TABLE brick_chunks (...)` | ✅ 없음 — main은 이 테이블을 모르니 무시 |
| `ALTER TABLE scenes ADD COLUMN` | ⚠️ 대체로 안전하나 권장 안 함 |
| `ALTER TABLE scenes DROP / RENAME` | 🔴 **main 즉시 깨짐** |

**이 브랜치의 규칙: 새 테이블만 만들고 기존 테이블은 손대지 않는다.**

- 🚫 기존 `0001`~`0008` 파일 수정 / 번호 재정렬 / 삭제 금지 (이미 적용된 마이그레이션을 고치면 DB와 파일이 어긋난다)
- 정말 기존 테이블을 바꿔야 하면 → **별도 Supabase 프로젝트**를 만들어 `.env.local`만 교체 (무료 플랜도 2개 가능)
- **P0에는 마이그레이션이 필요 없다** — 메모리 + localStorage로 충분. 데이터 포맷은 만들어 보면 반드시 바뀐다

## 8.5 지식재산(IP) 경계 — 설계 제약

> ⚠️ **법률 자문이 아니다.** 공개 판례로 확인되는 사실관계와, 그로부터 나오는 **설계 규칙**만 적는다.
> **상업 출시 전 IP 전문 변호사 검토 필요.**

### 갈리는 지점 — "브릭 형태"와 "레고 브랜드"는 정반대다

| 대상 | 상태 | 근거 |
|---|---|---|
| 스터드-튜브 결합 **특허** | **만료** | 1958 원본 및 후속 전부. 호환 브릭 제조사(메가블럭·코비 등)의 근거 |
| 브릭 **형상**의 3D 상표 | **레고 패소** | CJEU 2010 (Lego Juris v OHIM, C-48/09 P) — *기술적 결과에 필요한 형상은 상표가 될 수 없다* / 캐나다 대법원 2005 (Kirkbi v Ritvik) — 기능성 원칙 |
| **치수·비율** (8mm : 3.2mm) | **위험 낮음** | 숫자는 IP 대상이 아니다. 게다가 우리는 **물리 브릭을 만들지 않는다** — 실제 레고에 끼울 물건이 아니라 화면 비율(0.5m : 0.2m)일 뿐 |
| **"LEGO" 이름 · 로고** | 🔴 **완전 보호** | 절대 사용 금지 |
| **스터드 윗면 각인** | 🔴 보호 | 실제 레고 스터드엔 "LEGO"가 새겨져 있다. **우리는 넣지 않으며 앞으로도 넣지 않는다** |
| **미니피겨** | 🔴 **보호됨** | EU 일반법원 2015 (Best-Lock v OHIM) — 미니피겨 3D 상표 **유효**. 브릭과 달리 레고가 지켰다 |
| 특정 세트·모델·캐릭터 | 🔴 저작권 | 닌자고·시티 등. 라이선스물(스타워즈)은 별개 IP |
| 색 팔레트 | 🟢 낮음 | 색은 보호가 약하다 |

**단, 무풍지대는 아니다**: EU 일반법원 2021 (Delta Sport v EUIPO, T-515/19)에서 레고 브릭의 **등록디자인**이 "모듈 시스템 예외"로 살아남았다. 특정 등록디자인 건이라 기본 브릭 전반이 막힌다는 뜻은 아니지만 **"판례가 다 우리 편"이라고 단정하면 안 된다.** 또한 레고는 경고장을 매우 적극적으로 보낸다 — **이길 수 있는 사건도 대응 비용이 든다.**

### 설계 규칙 (지킬 것)

1. **사용자 화면·마케팅에 "레고/LEGO" 표기 금지.** "브릭/블록"(일반명사)만 쓴다. *"레고 호환"도 금지.*
2. **스터드에 각인을 넣지 않는다.**
3. **미니피겨를 만들지 않는다.** 캐릭터가 필요하면 미니피겨 실루엣(사다리꼴 머리·집게손·특유 몸통)을 피한 독자 디자인.
4. **프리셋 이름을 레고 세트명으로 짓지 않는다.**
5. 상업 출시 전 변호사 검토.

### 사용자가 레고 제품을 재현하는 경우

우리에겐 **공개 갤러리·리믹스**가 있어 가정이 아니라 실제 노출면이다.

| | 책임 |
|---|---|
| 개인적으로 따라 만듦 | 낮음(사적 이용) |
| 공개·공유 | **사용자 책임** — 특정 세트 디자인은 저작권 대상 |
| **플랫폼** | **관리 가능** — 아래 조건 충족 시 |

온라인서비스제공자 면책(한국 저작권법 §102~103, 미국 DMCA 세이프하버) 조건:
①침해를 **유도·조장하지 않을 것** ②**신고·삭제 절차**를 갖출 것 ③유효 신고에 **신속 대응** ④**반복 침해자 정책**.

→ **해야 할 일**: 이용약관 IP 조항 보강(`/legal/terms`) · 갤러리 **신고 버튼 + 삭제 절차** · 반복 침해자 방침.
→ **하지 말 것**: "레고 세트를 그대로 만들어보세요" 류 마케팅 · 세트 템플릿/조립도 제공 · 라이선스 캐릭터 포함.

**선례**: LDraw(수십 년) · LeoCAD · BrickLink **Stud.io**(레고가 BrickLink를 인수해 현재 레고 소유) — 사용자가 브릭 모델을 만들고 공유하는 디지털 도구는 공개적으로 존재한다. **카테고리 자체는 성립한다.**

### 시각적 차별화 — 검토했고 **보류**

"돌기를 윗면 말고 5면에 넣어 어느 방향이든 끼우게 하자"는 안을 검토했다. **두 목적이 섞여 있어 분리했다.**

| 목적 | 판단 |
|---|---|
| (a) 레고와 시각적으로 달라지기 | 효과는 있으나 **더 싼 수단이 있다** — 돌기 *모양*만 바꾸기(속 빈 링 스터드·모따기·육각). 룩은 브릭 그대로면서 레고의 민짜 원기둥과 구별됨. 삼각형 증가 0, 스터드 컬링 로직 그대로 |
| (b) 어느 방향이든 끼우기 | **지오메트리 문제가 아니다.** 방향 자유도는 **배치 규칙**이 정한다(현재 드롭 모델). 돌기를 5면에 붙여도 규칙을 안 바꾸면 여전히 위로만 쌓이고, 규칙만 바꾸면 돌기 없이도 옆에 붙는다 |

5면 돌기의 비용: 2×4 브릭 268 → **~652 삼각형**(2.4배), 스터드 컬링 변형 2종 → **최대 32종**(면마다 가려짐 판정), 룩이 크게 바뀜.

**→ 보류.** 급하지 않다 — **저장 포맷엔 `partId`만 들어가고 메시는 코드에 있어서, 나중에 바꿔도 기존 월드가 깨지지 않는다**(격자 비율과 달리 되돌릴 수 있는 결정).

## 9. 열린 질문 (구현하며 결정)

- **리전 크기** — 4×4×4 청크가 적정한지는 실제 draw call 프로파일로 확인
- **부분 스터드 가림** — "전부 덮임"만 처리하는 단순화가 시각적으로 충분한지
- **회전 축** — Y 4방향으로 충분한지 (경사 브릭 도입 시 재검토)
- **스터드 정렬 규칙** — 진짜 레고처럼 스터드 위에만 붙게 할지, 격자만 맞으면 되게 할지
- **브릭 월드와 기존 오브젝트의 공존** — 같은 씬에 GLB·라이트·모터가 함께 있을 때 선택/기즈모 UX
- **undo** — 브릭 편집은 현 스냅샷 방식(`HistoryEntry`가 `objects` 전체 복사)에 못 태운다. **델타 기반 undo 필요**
